## 1. 目标与范围

### 1.1 本任务要解决什么

对现有「离线缓存 + 数据同步」做**整体方案重设计**，并补齐按软件开发流程组织的全套 md 文档，使文档可直接指导开发。

### 1.2 现状（实测，非推断）

| 维度 | 现状实现 | 位置 |
| --- | --- | --- |
| 本地存储 | **单一 `EncryptedSharedPreferences`**（`SecureStore` 收口，含明文→密文一次性迁移） | `data/Prefs.kt`、`core/SecureStore` |
| 规则缓存 | 全局关键词/viewIds/selectors + 逐包 `pkg_kw:*`/`pkg_vid:*`/`pkg_sel:*` + 禁用集合；**整体覆盖经单次 edit 原子提交** | `Prefs.replaceAllRules`、`RulesStore` 契约 |
| 统计缓存 | 计数（总数 + 逐包）与日志（上限 200 条，JSON 数组单键）同存于 SP；计数经 `StatsRepository` 合批 5s 落盘 | `data/StatsRepository.kt`、`data/StatsStore.kt` |
| 增量/全量 | **仅增量探测**：`If-None-Match` + `rules_hash`，304 即跳过；命中 200 则**全量覆盖** | `net/SyncClient.kt` |
| 同步调度 | `JobScheduler` 周期 12h + `setPersisted(true)` + `NETWORK_TYPE_ANY`；无退避、无手动触发以外的事件触发 | `sync/SyncJobService.kt` |
| 冲突解决 | **无冲突概念**——单写者模型：云端单向覆盖本地规则，本地编辑无版本号 | `RulesRepository.applyCloudRules` |
| 离线写入 | **规则侧无离线写队列**（本地编辑直写 SP）；**上报侧无队列**，`reportSkip` 失败即静默丢弃（含 v1→v0 回退） | `SkipAdService.kt:296`、`SyncClient.reportSkip` |
| 网络恢复 | 无 `NetworkCallback`；仅靠 JobScheduler 的周期窗口 + 用户手动同步 | 全仓 grep 无 `registerNetworkCallback` |
| 安全 | HMAC-SHA256 验签（失败关闭）+ 证书固定（未配 = 拒连）+ 强制 HTTPS + 响应体 2MB 上限 + 条目数上限 | `SyncClient.securityGuard` |
| 服务端存储 | JSON 分片文件 + `tmp` + `renameSync` 原子写；单进程读多写少 | `server/src/storage/store.ts` |

### 1.3 范围内

1. 技术路线重选：瓶颈分析 → 2–3 套候选路线对比 → 选型理由与最终路线（本地存储 / 同步策略 / 冲突解决 / 增量与全量 / 网络恢复与重试）。
2. 方案设计：本地数据模型与缓存结构、离线写入队列、同步触发时机、冲突检测与合并规则、一致性保障、安全存储与异常兜底。
3. 开发路线重设计：可执行里程碑与阶段任务，含交付物、依赖关系、验收标准。
4. 全套 md 文档产出，结构统一、内容一致、可直接指导开发。

### 1.4 范围外（明确不做，避免蔓延）

| 不做的事 | 理由 |
| --- | --- |
| 服务端 JSON → `bun:sqlite` 迁移（既有 **R2**） | 已由 `DESIGN-ARCH-EVOLUTION.md` 界定为独立工程批次；本方案**只依赖其「API 响应形状零变化」承诺**，不并入 |
| `DESIGN-MODULE-REARCH.md` 的**分层/模块化重构**（`core:*` / `capability:*`） | 该文自述驱动因素是「覆盖率」，与本方案正交；本方案**只依赖其模块边界结论**，不接管其迁移顺序 |
| L2/L3/L4 能力层实现（VPN/防摇一摇/通知） | 属 `ROADMAP-ADS.md` 能力里程碑，与存储同步无依赖 |
| 重写为跨平台 / 更换 UI 框架 | 既有重写触发判据（`DESIGN-ARCH-EVOLUTION.md` §3）一条未触发 |
| `security-crypto` 1.1.0-alpha07 → DataStore 迁移 | 该文列为 **R1 的 spike**，结论未回填；本方案将其作为**待确认项 A**（§5），不擅自决策 |

### 1.5 不变量（重设计不得破坏）

以下为现状已有硬契约，任何路线都必须保持（列出以便后续文档逐条对账）：

1. `RulesStore.replaceAllRules` 是**唯一多键规则写入路径**，必须单次原子提交（防「半新半旧」）。
2. `StatsStore.addSkips` 是**计数唯一写入路径**；`appendLog` 不得顺带改计数（防「双重累加」）。
3. 云端规则必须**验签通过才可落地**，失败关闭；未配密钥/未配证书指纹一律拒绝。
4. 上报同样走证书固定通道，未配 pins 时 fail-closed 拒发。
5. 日志不回显完整 URL（只留主机名）。
6. 响应体与条目数有上限（2MB / 2000 应用 / 512 项 / 128 选择器 / 256 字符）。
7. `ArchitectureBoundaryTest` 的 9 条依赖规则继续成立（`ui` 不直读 `Prefs`、不碰 `SyncClient`/`SyncJobService`）。
8. `engine/` 保持零 Android 依赖。

## 4. 候选路线草案（**仅为对比框架，结论待 P2 产出**）

> 下列内容用于界定 P2 的对比范围，**不是结论**，不得直接引用为决策。

### 4.1 本地存储方案

| 候选 | 要点 | 已知代价 |
| --- | --- | --- |
| A. 沿用 `EncryptedSharedPreferences` + 端口抽象 | 零迁移；已验证原子性 | 无查询能力；大集合读写放大；上游 alpha 依赖 |
| B. **Room（SQLite）+ Keystore 自管字段加密** | 可查询、可分页、事务、容量可控 | 新增依赖与迁移成本；加密字段需自管；与 `SecureStore` 迁移测试兼容性待验证 |
| C. DataStore（Proto/Preferences）+ Keystore | 无 alpha 依赖风险；Flow 原生 | 无关系查询；大对象仍需自管文件 |

### 4.2 同步策略 / 冲突解决 / 增量与全量 / 网络恢复

| 维度 | 候选 |
| --- | --- |
| 同步策略 | ① 交替：拉为主 + 事件补（现状增强）；② 双向：本地写队列 + 服务端裁决；③ 服务端主导 + 客户端只读缓存 |
| 冲突解决 | ① 服务端裁决（last-write-wins + 版本号）；② 客户端三向合并（base/ours/theirs）；③ 无冲突模型（分区所有权：规则归服务端、用户偏好归本地） |
| 增量与全量 | ① 仅 hash + 304（现状）；② **按实体游标 + 增量 patch**；③ 定期全量校验（hash 对账）+ 平时增量 |
| 网络恢复与重试 | ① JobScheduler 单点（现状）；② `ConnectivityManager.NetworkCallback` 事件 + 指数退避 + 抖动；③ WorkManager（新建依赖）统一约束/退避/串链 |

**关键取舍提示**：候选 3（WorkManager）与候选 1（JobScheduler）在**零新依赖**与**既有基建复用**上冲突——现状已用 `JobScheduler` 且 `bun` 服务端零依赖是项目既定承诺，故重试机制倾向在 `JobScheduler` 之上自建退避并补 `NetworkCallback`，但这**必须在 P2 以证据论证后写进 ADR**，本计划不预判。

## 5. 需要你确认的关键假设与待确认项

> 以下每项在未获确认前，后续正文一律标注 `[待确认]`，不做臆断。

### A. 存储技术路线是否允许引入新的持久化框架？（影响面最大）

- **问题**：是否允许引入 **Room** 或 **WorkManager** 等新依赖？
- **背景**：现状是「零新增依赖」的严格克制（服务端 `bun` 零运行时依赖、客户端仅 OkHttp + security-crypto）。而「离线写入队列 + 幂等上报 + 可靠重试」若纯手写，需要自己实现持久化队列、退避、进程死亡恢复——**可靠性与代码量都会上升**。
- **选项**：① 严格零新依赖（手写队列 + `JobScheduler` 退避）；② 只允许 Room（存储层）；③ 只允许 WorkManager（调度层）；④ Room + WorkManager 都允许。
- **我的建议（待你裁定）**：倾向 ②（Room 仅用于**离线队列与需查询的数据**，规则缓存沿用经端口封装的现有存储以保住已验证的原子性契约）；理由须在 P2 用证据论证。

### B. 需求分析文档的落位前缀

- **问题**：`REQUIREMENTS-OFFLINE-SYNC.md` 放 `docs/planning/`（沿用现有目录，不新建目录），还是新建 `docs/requirements/`？
- **影响**：新建目录需改 `ProjectStructureTest` 白名单 + 文档地图，成本略高但语义更清晰。
- **我的建议**：放 `docs/planning/`，不新建目录（降低门禁变更面）。

### C. 服务端是否允许配套改造？

- **问题**：客户端离线队列要「不丢、不重」，通常需服务端提供**幂等键 / 批量确认 / 游标增量**支持。当前服务端仅有 `POST /api/v1/reports/batch`（批量上报）与 `GET /api/v1/rules/latest`。
- **选项**：① 服务端可改（新增幂等与游标字段）；② 服务端冻结，客户端单侧解决（可能牺牲「精确一次」，退化为「至少一次 + 客户端去重」）；③ 允许新增字段但不改既有语义。
- **我的建议**：③，并在 P5 明确兼容策略；同时**不并入 R2（SQLite）范围**。

### D. 一致性目标的强度

- **问题**：三类数据的一致性目标分别定到哪一档？
  - 规则：**强一致**（宁可不同步也不落半新半旧）——现状已是这个语义；
  - 统计计数：**最终一致**（可丢可重需明确）；
  - 上报事件：**至少一次**（允许重复，服务端去重）还是**精确一次**（需服务端幂等键）？
- **我的建议**：规则强一致、计数最终一致、上报至少一次 + 服务端幂等去重（成本最低）。

### E. 版本承载与里程碑编号

- **问题**：本方案挂在哪个版本序列？`ROADMAP.md` 已声明「重置后各里程碑用什么版本号尚未决策」，且 `3.x` 行为重置前历史。
