# Software Development Full Skill

> 适用范围：新项目开发、已有项目修改、Bug 修复、重构、代码审查、测试、API/数据库开发、前端/后端、脚本、CLI、嵌入式与毕业设计项目。
>
> 规则等级：`MUST` = 强制；`SHOULD` = 默认遵循；`MAY` = 可选。
>
> 核心原则：先理解，再设计；小步修改；保持可运行；用测试和工具验证；最小化不必要复杂度；让每次改动都可解释、可回退、可验证。

## 0. 总体行为协议

### 0.1 优先级

按以下顺序处理冲突：

1. 用户明确要求。
2. 项目自身规则：AGENTS.md、CLAUDE.md、CONTRIBUTING.md、README、架构文档、CI 约束等。
3. 本 Skill。
4. 语言/框架/工具官方约定。
5. 一般工程最佳实践。

当项目规则与本 Skill 冲突时，以项目规则为准，并在最终说明中指出影响。

### 0.2 基本工作方式

- MUST 先检查工作区状态和项目结构，再修改代码。
- MUST 优先读取现有实现、配置、测试和调用链，不凭文件名猜测行为。
- MUST 先定位真正的修改边界，再开始写代码。
- MUST 优先最小变更，不进行无关的大规模重排。
- MUST 保持项目在可运行、可构建或至少可验证状态。
- MUST 对关键结论提供验证证据：测试、构建、lint、类型检查、运行结果或静态分析。
- MUST NOT 为了“看起来更好”而无理由改动大量不相关文件。
- MUST NOT 伪装不确定性；无法验证时明确说明。

### 0.3 输出要求

完成任务后，默认报告：

- 改了什么。
- 为什么这样改。
- 改动涉及哪些文件/模块。
- 如何验证。
- 验证结果。
- 已知风险或未解决事项。

## 1. 开始任务前：项目侦察

### 1.1 必查项目规则

MUST 搜索并读取可能存在的：

- `AGENTS.md`
- `CLAUDE.md`
- `CURSOR.md` / `.cursorrules`
- `CONTRIBUTING.md`
- `README.md`
- `.editorconfig`
- `Makefile` / `Taskfile.yml`
- `package.json` / `pyproject.toml` / `pom.xml` / `build.gradle` / `Cargo.toml` / `go.mod` 等
- CI 工作流
- 测试配置
- lint / formatter / type checker 配置

如果项目存在多个层级规则文件，遵循离目标文件最近且适用范围最具体的规则。

### 1.2 建立最小心智模型

在开始实现前，至少回答：

- 项目入口在哪里？
- 核心业务/功能模块在哪里？
- 数据从哪里进入，在哪里变化，最后输出到哪里？
- 主要依赖与外部边界是什么？
- 当前测试入口是什么？
- 构建、运行、部署命令是什么？
- 本次需求影响哪些模块？

### 1.3 先读调用链，再改局部

对于 Bug 或功能修改，优先建立：

`入口 -> 调用者 -> 目标函数/类 -> 依赖 -> 副作用 -> 输出`

不要只改报错位置，而忽略上游输入、状态生命周期和下游假设。

## 2. 需求分析

### 2.1 将自然语言转为可验证目标

将需求拆成：

- 必须新增的行为。
- 必须保持不变的行为。
- 输入与输出。
- 错误情况。
- 权限/安全要求。
- 性能约束。
- 兼容性约束。
- 完成标准（Definition of Done）。

### 2.2 边界条件

MUST 主动考虑：

- 空值 / 缺失值。
- 空集合。
- 极小/极大值。
- 重复输入。
- 非法输入。
- 并发调用。
- 网络/磁盘/数据库失败。
- 超时。
- 重试导致的重复执行。
- 服务重启或进程崩溃。
- 配置缺失。
- 版本不兼容。

### 2.3 避免伪需求

不得因为“可能以后会用”就默认加入：

- 泛型框架。
- 插件系统。
- 多层抽象。
- 配置中心。
- 事件总线。
- 工厂/策略/装饰器等模式。
- 不必要的数据库表。
- 不必要的缓存。

YAGNI：当前没有真实需求支撑的复杂度，不应提前引入。

## 3. 设计原则

### 3.1 单一职责

一个函数、类、模块应有清晰且相对单一的变化原因。

避免：

- Controller 同时查询数据库、执行业务规则、发送消息。
- UI 组件直接操作数据库。
- Domain 对象直接调用 HTTP SDK。
- 一个工具类聚集完全无关的功能。

### 3.2 高内聚、低耦合

- 相关行为放在一起。
- 不相关行为不要因为“方便”塞进同一模块。
- 减少跨模块的隐式状态和全局变量。
- 优先显式参数和返回值，而不是隐藏依赖。

### 3.3 深模块、简单接口

优先让模块内部承担复杂度，对外提供少量稳定接口。

避免浅层抽象：

`调用者 -> 包装器 -> 转发器 -> 再包装 -> 真实实现`

如果中间层没有提供真正的策略、隔离、转换或业务价值，应考虑删除。

### 3.4 信息隐藏

模块外部只应知道完成任务所必须知道的信息。

隐藏：

- 数据结构细节。
- 第三方 SDK 类型。
- 数据库存储细节。
- 线程/锁实现细节。
- 内部缓存机制。
- 内部状态机。

### 3.5 依赖倒置

高层策略不应依赖低层实现细节。

推荐：

`业务策略 -> 抽象接口 <- 基础设施实现`

不推荐：

`业务策略 -> MySQLClient / RedisClient / Axios / FrameworkContext`

## 4. Clean Architecture 规则

### 4.1 依赖方向

MUST 保持依赖向稳定的业务规则方向指向内部。

推荐分层：

```text
Domain
  ↑
Application / Use Cases
  ↑
Interface Adapters
  ↑
Infrastructure / Frameworks / External Systems
```

越靠内层越稳定；越靠外层越可替换。

### 4.2 Domain 层

可以包含：

- 实体。
- 值对象。
- 领域规则。
- 不变量。
- 核心业务计算。

MUST NOT 直接依赖：

- Web 框架。
- ORM。
- 数据库驱动。
- UI。
- HTTP 客户端。
- 环境变量。
- 文件系统。
- 云厂商 SDK。

### 4.3 Application 层

负责：

- 用例编排。
- 输入/输出模型。
- 事务边界。
- 权限检查协调。
- 调用端口。

Application 不应成为“万能 Service 垃圾桶”。

### 4.4 Adapter 层

负责：

- Controller。
- Presenter。
- DTO 映射。
- 参数解析。
- 外部模型转换。
- Gateway Adapter。

### 4.5 Infrastructure 层

包含：

- 数据库。
- ORM。
- HTTP client。
- 消息队列。
- 文件系统。
- 云 SDK。
- Framework bootstrap。
- 配置装配。

Infrastructure 实现内层定义的接口，不把供应商类型泄漏给业务层。

### 4.6 禁止绕层

禁止常见模式：

- Controller 直接操作数据库。
- UI 直接调用持久化实现。
- Domain 调用第三方服务。
- Repository 接口定义在 Infrastructure 后被 Domain 依赖。
- 为了省几行代码而绕过 Use Case。

确有架构例外时，必须说明原因和影响。

## 5. 项目结构

### 5.1 优先按业务能力组织

优先：

```text
features/
  user/
  order/
  payment/
```

而不是无脑：

```text
controllers/
services/
utils/
models/
```

当技术分层确实更适合项目时，可以使用分层结构；关键是不要让目录名掩盖真实业务边界。

### 5.2 防止垃圾桶目录

慎用并持续清理：

- `utils`
- `helpers`
- `common`
- `misc`
- `shared`
- `base`
- `core`

加入这些目录的每个文件，都应有明确归属与复用理由。

## 6. 命名规则

### 6.1 名称必须揭示意图

优先：

- `calculateOrderTotal`
- `findActiveUser`
- `validateToken`
- `buildPaymentRequest`

避免：

- `doIt`
- `handle`
- `process`
- `data`
- `temp`
- `manager`
- `helper`

### 6.2 布尔值

优先使用能够读出真假语义的名称：

- `isActive`
- `hasPermission`
- `canRetry`
- `shouldRefresh`

### 6.3 一致性

同一领域概念只能有一个主名称，避免：

`userId / uid / memberId / accountId`

在确有不同语义时才允许不同名称。

## 7. 函数规则

### 7.1 小而完整

函数应尽量只做一个明确任务。

优先拆分：

1. 解析。
2. 验证。
3. 业务计算。
4. 持久化/IO。
5. 输出格式化。

### 7.2 一个抽象层级

不要在一个函数里混合：

- 业务规则。
- SQL 细节。
- HTTP header 操作。
- UI 字符串拼接。

### 7.3 控制流

优先使用 guard clause 减少不必要嵌套。

避免：

```text
if A {
  if B {
    if C {
      ...
    }
  }
}
```

在逻辑更清楚的前提下改为早返回。

但不要为了“减少 if”而引入复杂模式。

### 7.4 副作用

副作用必须显式、可定位。

尤其注意：

- 全局状态。
- 隐式缓存。
- 自动写数据库。
- 隐式网络请求。
- 隐式日志/埋点。
- 修改传入对象。

## 8. 类与模块

- MUST 保持模块边界明确。
- SHOULD 优先组合而非继承。
- 避免 God Object。
- 避免拥有大量字段和大量互不相关方法的类。
- 删除不再有价值的抽象。
- 共享逻辑必须共享“知识”，而不是机械合并重复代码。

### 8.1 DRY 的正确理解

不要为了两段偶然相似的代码马上抽象。

真正应该消除的是“重复知识”和“重复业务规则”。

过早抽象会造成：

- 强耦合。
- 参数爆炸。
- 通用函数难以理解。
- 一个需求修改影响多个无关调用方。

## 9. 数据与状态

### 9.1 尽量限制可变状态

- 缩小变量作用域。
- 尽量使用不可变中间值。
- 集中状态迁移逻辑。
- 避免多个模块共同写同一状态。

### 9.2 状态机

当业务状态存在明确合法转换时，应显式建模，不要依赖散落在各处的 `if`。

例如：

```text
PENDING -> PAID -> SHIPPED -> COMPLETED
PENDING -> CANCELLED
```

禁止隐含非法转换，除非业务明确允许。

## 10. 错误处理

### 10.1 先区分错误类型

至少区分：

- 用户输入错误。
- 业务规则错误。
- 权限错误。
- 外部依赖错误。
- 系统内部错误。
- 配置/部署错误。

### 10.2 错误语义

- 不吞异常。
- 不用空返回值掩盖真实错误。
- 不以“万能 catch”替代错误治理。
- 错误信息应便于定位问题，但不得泄漏秘密。

### 10.3 重试

只有在确认操作具备幂等性或有去重机制时才重试。

重试策略应考虑：

- 最大重试次数。
- 指数退避。
- 抖动。
- 超时。
- 哪些错误可以重试。

禁止对明确的业务拒绝、参数错误无限重试。

## 11. 日志与可观测性

日志必须服务于诊断，不是越多越好。

建议包含：

- 时间。
- 请求/事务/trace 标识。
- 事件名称。
- 关键实体标识。
- 失败原因。
- 延迟或耗时（关键路径）。

禁止输出：

- 明文密码。
- token。
- API key。
- 私钥。
- 完整信用卡数据。
- 不必要的个人敏感数据。

对于关键服务，SHOULD 设计：

- metrics。
- structured logs。
- tracing。
- health check。
- readiness/liveness。

## 12. 配置与环境

- 配置与代码分离。
- 秘密不得硬编码进代码仓库。
- 配置读取应在边界层完成。
- 核心业务不应直接读取环境变量。
- 提供明确的配置校验与缺省策略。

## 13. API 设计

### 13.1 输入输出契约

API 应明确：

- 输入字段。
- 类型。
- 必填性。
- 约束。
- 错误码。
- 输出结构。
- 兼容性策略。

### 13.2 DTO 与领域模型

不要默认把数据库模型或 ORM 实体直接作为公共 API 输出。

外部 DTO 与内部领域模型之间应有明确边界。

### 13.3 兼容性

修改接口前检查：

- 调用方。
- SDK。
- 文档。
- 数据迁移。
- 旧版本客户端。
- 回滚策略。

优先向后兼容的增量变更。

## 14. 数据库

### 14.1 Schema

数据库设计必须服务真实业务约束，而不是只服务当前代码结构。

考虑：

- 主键。
- 唯一约束。
- 外键或引用完整性。
- 索引。
- NULL 语义。
- 时区。
- 精度。
- 数据生命周期。

### 14.2 查询

- 避免 N+1。
- 不要默认 `SELECT *`。
- 大表谨慎全表扫描。
- 为真实查询模式设计索引。
- 删除/更新前确认影响范围。

### 14.3 迁移

数据库迁移必须考虑：

1. 旧代码是否还能工作。
2. 新代码何时开始依赖新结构。
3. 部署顺序。
4. 回滚策略。
5. 数据量与迁移成本。

## 15. 并发与异步

必须明确：

- 哪些资源共享。
- 哪些数据需要同步。
- 哪些操作可并行。
- 哪些操作必须串行。
- 是否存在竞态。

避免：

- 无边界的并发。
- 无限创建线程/任务。
- 未受控队列。
- 使用 sleep 掩盖同步问题。

优先使用：

- bounded concurrency。
- timeout。
- cancellation。
- backpressure。
- lock 的最小作用范围。

## 16. 性能

### 16.1 先测量再优化

除非存在明显的算法级问题，否则不要凭感觉优化。

性能优化应回答：

- 瓶颈是什么？
- 如何测量？
- 优化前是什么？
- 优化后是什么？
- 是否增加复杂度？

### 16.2 常见优先级

通常先处理：

1. 错误算法/数据结构。
2. 不必要的 I/O。
3. N+1 查询。
4. 不必要的网络调用。
5. 热路径中的重复计算。
6. 才考虑微优化。

## 17. 安全开发

### 17.1 输入永不可信

所有外部输入都应视为不可信：

- HTTP 参数。
- 文件。
- 用户上传内容。
- 环境变量。
- 消息队列。
- Webhook。
- 第三方 API。

### 17.2 常见安全要求

必须检查：

- SQL injection。
- Command injection。
- XSS。
- CSRF。
- SSRF。
- Path traversal。
- 不安全反序列化。
- 越权访问。
- 密钥泄漏。
- 日志泄漏。

### 17.3 权限

不要只依赖前端隐藏按钮。

真正的数据和操作权限必须在可信后端/业务边界验证。

### 17.4 依赖安全

- 避免明显废弃或有严重已知漏洞的依赖。
- 升级依赖前检查兼容性与变更日志。
- 不盲目升级整个依赖树。

## 18. 测试总则

### 18.1 测试金字塔

优先：

- 单元测试。
- 集成测试。
- 少量端到端测试。

不要把所有逻辑都堆到 E2E。

### 18.2 测试行为，不测试实现细节

测试应优先验证：

- 输入 -> 结果。
- 状态 -> 行为。
- 外部契约。
- 业务不变量。

避免测试私有实现细节，除非确有必要。

### 18.3 新增功能

默认流程：

1. 明确成功场景。
2. 明确失败场景。
3. 明确边界条件。
4. 添加/更新测试。
5. 实现功能。
6. 运行相关测试。
7. 再运行更广范围验证。

### 18.4 Bug 修复

原则：

> 先建立能复现问题的测试，再修代码。

修复后测试必须证明原 Bug 不再出现。

## 19. Legacy Code

对于缺乏测试、结构混乱的遗留系统：

1. 先不要大重写。
2. 先识别可测试边界。
3. 添加 characterization test（特征测试）。
4. 利用 seam 打开可替换点。
5. 用小步重构降低风险。
6. 再实施功能变化。

遗留代码“不好看”不是立即重写的充分理由。

## 20. 重构协议

### 20.1 重构定义

重构是：

> 在不改变可观察行为的前提下改善内部结构。

### 20.2 推荐顺序

```text
理解当前行为
    ↓
建立安全网
    ↓
准备性重构
    ↓
实现功能变化
    ↓
后续清理
    ↓
验证
```

### 20.3 常见安全重构

优先：

- 重命名。
- 提取函数。
- 提取变量。
- 移动函数/字段到正确模块。
- 隔离副作用。
- 合并重复知识。
- 简化条件分支。
- 删除死代码。

### 20.4 重构停止规则

满足以下任一条件就应停止：

- 目标需求已经容易实现。
- 阻碍修改的主要坏味道已经消除。
- 继续整理变得主观或投机。
- 新抽象没有明确收益。
- 改动范围开始明显偏离用户需求。

## 21. Git 规则

### 21.1 工作前

MUST 检查：

```bash
git status
git branch --show-current
git log -5 --oneline
```

必要时确认远端和最近相关提交。

### 21.2 修改过程中

- 保持提交粒度清晰。
- 不覆盖用户已有修改。
- 不执行危险的 `reset --hard`、强制 push 等命令，除非明确得到授权。
- 不把无关格式化、依赖升级塞进功能提交。

### 21.3 提交信息

提交信息应说明“做了什么”，而不是“修改了一些文件”。

推荐：

```text
fix: prevent duplicate payment requests
feat: add user export endpoint
refactor: isolate email gateway
```

## 22. 代码审查规则

审查顺序：

### A. 正确性

- 是否满足需求？
- 是否存在明显 bug？
- 是否破坏已有行为？

### B. 数据与并发

- 边界是否正确？
- 是否有竞态？
- 是否有重复执行？

### C. 架构

- 依赖方向正确吗？
- 是否绕层？
- 是否泄漏基础设施类型？

### D. 可维护性

- 名称清楚吗？
- 函数责任清楚吗？
- 是否引入不必要抽象？

### E. 安全

- 输入验证？
- 权限？
- 秘密？
- 日志？

### F. 测试

- 关键路径有测试吗？
- 测试是否验证真实行为？

## 23. Code Smell 清单

主动识别：

- 超长函数。
- 超长类。
- God Object。
- 深层嵌套。
- 重复逻辑。
- Shotgun Surgery。
- Divergent Change。
- Feature Envy。
- Primitive Obsession。
- Speculative Generality。
- Pass-through abstraction。
- 隐式全局状态。
- 过度参数化。
- 不必要继承。
- 跨模块直接访问内部细节。
- 难以测试的静态依赖。

发现坏味道时，不一定立即重构；首先判断它是否阻碍当前需求或提高实际风险。

## 24. 第三方依赖与外部 API

当行为依赖可能变化的库、SDK、框架或外部服务时：

- 优先检查当前官方文档与项目锁定版本。
- 不把记忆中的 API 当成事实。
- 优先遵循仓库当前已有用法。
- 升级依赖必须说明原因和兼容性影响。
- 对关键外部调用定义明确 timeout、错误处理与降级策略。

## 25. 文件与改动范围

原则：

- 只打开完成当前任务所需的文件。
- 先读，再改。
- 对生成文件、锁文件和构建产物保持谨慎。
- 不随意修改自动生成代码。
- 不把临时调试文件提交到仓库。

## 26. 文档规则

代码不能独立表达的重要决策，应记录在适当位置：

- README。
- ADR。
- API 文档。
- 架构文档。
- 注释。

注释应解释“为什么”，而不是重复“代码在做什么”。

不要写大段失真的注释来掩盖复杂代码；先简化代码。

## 27. 自动化与工具

优先使用项目已有自动化：

```text
format -> lint -> typecheck -> unit test -> integration test -> build
```

具体命令必须以项目实际配置为准，不凭空假设。

对于失败命令：

1. 读取错误上下文。
2. 判断是代码问题、环境问题、依赖问题还是测试基线问题。
3. 修复根因。
4. 重跑最相关的验证。
5. 必要时扩大验证范围。

## 28. 完成定义（Definition of Done）

任务在以下条件满足后才算完成：

- 用户要求已实现。
- 相关边界条件有处理。
- 关键路径有测试或合理验证。
- 格式化/lint/typecheck/build 等适用检查通过。
- 没有引入明显安全问题。
- 没有无关的大规模改动。
- 文档/配置需要同步时已经同步。
- 最终结果可被另一位开发者理解和复核。

## 29. 标准工作流

```text
[1] 读取项目规则
      ↓
[2] 检查 git/worktree
      ↓
[3] 定位入口与相关模块
      ↓
[4] 理解当前行为与调用链
      ↓
[5] 明确需求、约束、边界
      ↓
[6] 选择最简单可行设计
      ↓
[7] 建立或确认测试安全网
      ↓
[8] 小步实现
      ↓
[9] 运行格式化/lint/typecheck/测试
      ↓
[10] 检查架构、安全、性能
      ↓
[11] 查看 diff 与工作区
      ↓
[12] 最终报告改动、验证与风险
```

## 30. AI Agent 行为规则

### 30.1 不猜

不知道的事实必须：

- 从项目代码寻找证据；或
- 从官方文档验证；或
- 明确标记为推测。

### 30.2 不过度行动

不要因为发现一个旧问题，就顺手修复几十个无关问题。

### 30.3 不隐藏失败

失败的测试、构建、lint 不得在最终报告中省略。

### 30.4 不制造假成功

不得声称“已测试”“已构建”“已验证”，除非实际执行并得到结果。

### 30.5 修改现有代码时

默认先做局部修改；只有在以下情况才考虑较大范围重构：

- 当前结构无法安全实现需求。
- 主要坏味道直接制造风险。
- 有明确迁移路径。
- 有足够测试安全网。

## 31. 领域驱动设计（适用时）

当业务复杂且领域概念明显时，考虑：

- Entity。
- Value Object。
- Aggregate。
- Repository。
- Domain Service。
- Domain Event。
- Bounded Context。

不要为了“用了 DDD”而机械创建几十个类。

### 31.1 业务语言

代码中的核心概念应尽量贴近业务术语，使：

```text
需求描述 ≈ 代码概念 ≈ 测试名称 ≈ 文档术语
```

### 31.2 不变量

领域规则应尽可能集中，避免同一业务约束散落在 Controller、SQL、UI 和脚本中。

## 32. 生产可靠性

对于服务端、API、队列或关键集成，考虑：

- timeout。
- retry。
- idempotency。
- rate limit。
- circuit breaker。
- bulkhead。
- backpressure。
- graceful shutdown。
- health check。
- observability。
- dead letter / failure handling。

不是每个项目都必须实现全部机制；根据真实故障模式选择。

## 33. 数据密集型系统

涉及大量数据时，额外检查：

- 一致性要求。
- 事务边界。
- 并发控制。
- 数据模型。
- 复制。
- 分区。
- 缓存一致性。
- 读写模式。
- 数据保留策略。

任何“为了性能”引入的缓存，都必须明确失效策略。

## 34. 前端开发补充

### 34.1 UI 状态

明确区分：

- loading。
- success。
- empty。
- error。
- stale。
- disabled。

### 34.2 组件设计

组件应：

- 责任清楚。
- Props/API 简洁。
- 避免巨大组件。
- 避免深层隐式上下文依赖。

### 34.3 前端安全

- 不信任 URL 参数。
- 防止 XSS。
- 正确处理 token 生命周期。
- 不把秘密放进前端 bundle。

## 35. 后端开发补充

API 处理建议：

```text
Transport
  -> Validation
  -> Authentication / Authorization
  -> Use Case
  -> Domain
  -> Port
  -> Infrastructure
  -> Response mapping
```

业务逻辑不得全部集中在路由函数中。

## 36. 脚本与自动化补充

脚本也必须遵循工程纪律：

- 输入检查。
- 错误退出码。
- 幂等性。
- 日志。
- dry-run（危险操作适用）。
- 不破坏用户数据。
- 明确删除/覆盖范围。

## 37. 嵌入式开发补充

对于 MCU、机器人、Arduino、ESP32、STM32 等：

- 明确硬件资源边界。
- 避免阻塞式死循环掩盖控制问题。
- 明确采样周期。
- 明确中断上下文与主循环上下文。
- 外设访问与控制算法分离。
- 参数统一集中配置。
- 关键控制路径保持确定性。
- 修改控制算法后必须进行仿真、单元验证或实际安全测试（能做哪一种做哪一种）。

对于闭环控制系统尤其检查：

- 传感器零偏。
- 噪声。
- 饱和。
- 积分 windup。
- 采样周期抖动。
- 执行器限幅。
- 故障保护。

## 38. 毕业设计/教学项目补充

对于毕业设计、课程设计等项目：

- 代码必须与论文中描述的架构一致，或在文中明确说明演进。
- 核心算法需要给出输入、处理、输出和关键参数。
- 图表、流程图、系统结构图应与实际代码对应。
- 实验数据不得伪造。
- 测试结果应保留可追溯依据。
- 对关键公式和参数给出来源或推导。

## 42. 与外部规则库的关系

本 Skill 是面向实际 AI 编程任务的整合版规则，不逐字复制第三方规则文本。其设计思想综合了常见的软件工程原则，尤其包括：

- Clean Code：可读性、命名、函数责任、简单性。
- Clean Architecture：依赖规则、边界、业务与细节隔离。
- Refactoring：小步、保持行为、测试安全网。
- Software Design：降低复杂度、深模块、信息隐藏。
- DDD：业务语言、领域边界和不变量。
- Legacy Code：特征测试、缝隙和增量改造。
- Production Reliability：超时、重试、限流、隔离、观测。
- Pragmatic Engineering：自动化、快速反馈、避免过度工程化。

这些方向与公开的 `agent-rules-books` 项目所采用的规则体系一致，但本文件是重新组织后的独立工作协议。该项目目前将 `full` 定义为 canonical complete source，并覆盖 Clean Architecture、Clean Code、Refactoring、软件设计、可靠性、遗留代码等多类规则。
